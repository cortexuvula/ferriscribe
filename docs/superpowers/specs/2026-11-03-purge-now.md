# Spec: "Purge Now" — manual, exact-set permanent Trash purge

Approved by Andre (owner) via Frikkie's ordering message, 2026-11-03.
Scope: BUILD/TEST only. No real-DB purge, no install/launch, no commit/push/PR.

## User-facing behavior

A `Purge Now` button in the Trash toolbar (beside the restore controls,
danger styling, existing `ConfirmDialog`):

1. Click fetches a BACKEND preview (`preview_trash_purge`) — never derived
   from the loaded page, the local search filter, or `trashedTotal`.
2. The confirmation dialog shows the authoritative count from that preview,
   warns that ALL recordings in Trash are permanently deleted — audio,
   transcripts, SOAP notes, generated documents — with NO undo, and that the
   scope covers records outside the current search/loaded pages.
3. Confirm executes a destructive purge of the EXACT frozen candidate set
   reviewed in the dialog — never "whatever is in Trash now".
4. Result announces purged count; if rows were protected (mid-encryption) it
   says they were KEPT and suggests retrying later (never claims "Trash
   emptied" while they remain); if some audio removals were queued for retry
   it says cleanup is pending.
5. Cancel does nothing destructive and restores focus (ConfirmDialog behavior).
6. Button disabled when Trash is empty, while loading, on load error, and
   while a purge/restore is in flight (busy label `Purging…`).

## Snapshot (exact-set) contract

`preview_trash_purge` returns `candidates: [{id, deletedAt}]` — every
soft-deleted row regardless of deletion/creation age (includes freshest and
future-dated tombstones), excluding `encryption_pending` rows — plus
`protectedCount` (trashed rows still mid-encryption, reported honestly).

`purge_trash_now(candidates)` re-verifies EACH candidate INSIDE the deletion
transaction, by tombstone identity (id + the raw stored `deleted_at` string
from the preview), and additionally rechecks `deleted_at IS NOT NULL` and the
`encryption_pending IS NULL/0` guard:

- match + not encrypting → FTS-consistent delete + `purged_recordings`
  ledger write (same transaction), row counted purged.
- match but `encryption_pending` → PROTECTED: not deleted, not ledgered,
  artifacts untouched.
- no match (restored and left active, re-trashed with a NEW `deleted_at`,
  purged/gone already) → CHANGED: not deleted, not ledgered, artifacts
  untouched. Restore→re-trash is a new deletion requiring new consent.

This prevents: newly-trashed rows silently joining; same-count set swaps;
count-only validation. No giant token service — raw stored-string equality
is exact and format-agnostic.

## Purge-first artifact cleanup (transactional outbox)

The purge is ONE database transaction. Inside it: tombstone-identity
recheck, row DELETE, RAG-chunk deletion, FTS-consistent de-indexing, the
`purged_recordings` ledger write — and the DURABLE cleanup intent for
every purged row's audio path (merged, deduped, into the existing
`pending_file_removals` queue). Artifact paths are read from the live row
inside the transaction (never the stale preview).

- RAG vectors: deleted in the same transaction (a vector failure rolls the
  whole purge back — orphaned chunks are queryable with no recordings
  join, so they can never be left behind on a consented deletion).
- Durable intent BEFORE commit: once the transaction commits, every needed
  unlink has committed intent — a crash before cleanup, a failed unlink,
  or a failed acknowledgment all recover via the boot/tick drain. If the
  queue read/parse/write fails, the WHOLE purge rolls back (rows, chunks,
  FTS, ledger, and the queue itself) — no partial state, no orphan. A
  CORRUPT queue is never reset (fail closed).
- Ownership guard: a path still referenced by any SURVIVING row (shared
  path with a non-purged recording) is never enqueued and never unlinked.
  The drain re-validates ownership before every unlink: a stale intent
  re-bound to a live recording keeps the file and stays pending (never
  silently discarded, never deletes a live owner).
- Only AFTER commit does the immediate cleanup attempt run: unlink each
  intended path; success or NotFound acknowledges by removing ONLY that
  path (exclusive `BEGIN IMMEDIATE` read-modify-write, so concurrent
  enqueues cannot be erased). Any failure leaves the committed intent in
  place and the result reports cleanup pending — truthfully, because the
  drain WILL finish it.
- Retention sweeper: policy/windows unchanged; it shares the drain and the
  exclusive queue-write guard (its warn-only vector handling is untouched
  — retention has no per-action consent claim).

## Sync/ledger semantics (unchanged)

Manual purge writes the same local `purged_recordings` ledger the retention
purge writes, in the same transaction as the DELETE
(`ContentSyncRepo::merge_incoming` refuses stale peer copies via the
ledger). No new network protocol; no claim of erasing peer copies/backups.
Active recordings and the automatic retention setting are untouched.

## PHI discipline

New logs and error strings carry counts/ids only — never filenames or paths.
Frontend failure copy goes through the existing `sanitizedErr` discipline.

## Non-goals

No changes to retention sweeping cadence or age checks, no `days=0` hacks,
no trash_retention_days changes, no broad UI redesign, no new dependencies.
