# Training Corpus Design

**Status:** Draft — pending user review
**Date:** 2026-05-11
**Author:** Brainstorming session with Claude Code

## Goal

Let a clinician using FerriScribe build a private, on-device training corpus of (transcript, AI-draft, clinician-final-version) triples drawn from their own routine work, so that they (or someone with their consent) can later fine-tune an open-weight LLM toward their specific dictation style, specialty vocabulary, and formatting preferences. No data leaves the device unless and until the clinician deliberately exports it.

## Non-goals

- **Actual fine-tuning.** The training run itself happens outside this app (unsloth, mlx-lm, torchtune, axolotl, etc., per the clinician's preference and hardware). This spec covers data preparation only.
- **Multi-clinician aggregation.** This is a personal-model design; nothing in this spec assumes more than one clinician's data ever touches the same corpus.
- **Practice-server training data lake.** Out of scope.
- **Continuous learning / online fine-tuning.** Export is a deliberate one-shot action.
- **Inference-time model selection beyond Ollama's existing model list.** When the clinician finishes a fine-tune and pulls the resulting model into Ollama, it shows up in the existing AI provider list — no new runtime needed.

## Hard constraints honored

- **No PHI leaves the device.** All capture, curation, and export happens locally. The exported JSONL is written to a user-chosen directory on the same device.
- **No telemetry.** No counter or signal is sent anywhere about how many notes a clinician has captured, promoted, or rejected.
- **Local-only AI.** Drafts are generated by the existing Ollama / LM Studio providers — this feature adds no new provider.
- **Encrypted at rest.** New table inherits SQLCipher encryption automatically (same DB).

## Architecture overview

Three loosely-coupled phases, each its own UI surface:

```
   ┌────────────────────────────────────────────────────────────┐
   │  Phase 1: CAPTURE (automatic)                              │
   │  Every successful generation → row in `generations`         │
   │  Every save updates the matching row's `final_text`         │
   └────────────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌────────────────────────────────────────────────────────────┐
   │  Phase 2: CURATE (manual, deliberate)                       │
   │  Settings → Training Corpus tab                             │
   │  Per-row Promote / Reject / Skip; corpus_status updated     │
   └────────────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌────────────────────────────────────────────────────────────┐
   │  Phase 3: EXPORT (one-shot)                                 │
   │  Filter to promoted + non-null final_text                   │
   │  Apply extended PhiRedactor                                 │
   │  Emit JSONL + README + manifest to user-chosen directory    │
   └────────────────────────────────────────────────────────────┘

   Out of scope: the fine-tuning itself + pulling the resulting
   model into Ollama. Both standard, well-documented operations.
```

The phases are independently shippable: Phase 1 alone gives the clinician a draft-vs-final history (valuable for analytics even without the corpus feature). Phase 2 + 3 add the actual training-corpus surface.

## Data model

One new table, one FK, no changes to existing tables.

```sql
CREATE TABLE generations (
    id                    TEXT PRIMARY KEY NOT NULL,
    recording_id          TEXT NOT NULL,
    output_type           TEXT NOT NULL,
        -- 'soap' for v1; extensible to 'referral'/'letter'/'synopsis' later

    created_at            TEXT NOT NULL DEFAULT (datetime('now')),
    finalized_at          TEXT,

    -- AI-side context, captured at generation time. A corpus that mixes
    -- drafts from multiple base models without labeling produces a
    -- confused fine-tune; we always know which model drafted each row.
    ai_provider           TEXT NOT NULL,
    ai_model              TEXT NOT NULL,
    prompt_template_name  TEXT,

    -- Inputs snapshotted at generation time. The recording's transcript
    -- or context may be edited later; the training pair must remain
    -- coherent.
    input_transcript      TEXT NOT NULL,
    input_context_json    TEXT,

    -- The two halves of the training pair.
    draft_text            TEXT NOT NULL,
    final_text            TEXT,
        -- NULL = clinician never saved this draft (regenerated /
        -- abandoned). That's signal too — preserve as "rejected".

    corpus_status         TEXT NOT NULL DEFAULT 'candidate'
        CHECK (corpus_status IN ('candidate','promoted','rejected','excluded')),
    corpus_curated_at     TEXT,

    -- Derived signal, cached. Updated async after final_text is set.
    edit_distance         INTEGER,
    edit_ratio            REAL,

    -- 1 for the first generation attempt against this recording;
    -- bumped per regeneration.
    regeneration_seq      INTEGER NOT NULL DEFAULT 1,

    FOREIGN KEY (recording_id) REFERENCES recordings(id) ON DELETE CASCADE
);

CREATE INDEX idx_generations_recording      ON generations (recording_id);
CREATE INDEX idx_generations_corpus_status  ON generations (corpus_status, created_at DESC);
CREATE INDEX idx_generations_created        ON generations (created_at DESC);
```

### Design choices

- **Snapshot inputs, don't reference.** `input_transcript` and `input_context_json` are stored fully even though `recordings` already has the current versions. A future edit to a transcript shouldn't silently invalidate every training pair derived from it.

- **`final_text NULL` is a real value, not missing data.** It marks drafts the clinician rejected by regenerating or abandoning — valuable negative-signal data.

- **CASCADE on recording delete.** Mirrors the user's mental model and inherits the right-to-delete pattern.

- **`ai_provider` + `ai_model` are NOT NULL.** Required for clean multi-model corpus filtering at export.

- **`generations.final_text` and `recordings.soap_note` are redundant.** Both written in the same DB transaction on save. Future cleanup could deprecate the latter; v1 keeps both for backward compat.

- **No prompt-text capture.** Reconstructable from `prompt_template_name` + `input_context_json` + the template file. If template versioning becomes interesting, we can add it.

## Phase 1 — Capture

### When a row is inserted

After every successful AI generation that produces a SOAP draft. Specifically, immediately after the AI provider's `complete()` returns OK, inside the same Tauri command that returns the draft to the frontend. The row is inserted in a separate transaction from the response to the UI — capture failure must not break the user's workflow.

For v1, this hooks into the existing SOAP generation pipeline only (`output_type = 'soap'`). The hook point is a single `RecordingsRepo::record_generation(...)` (or equivalent) call, which makes future output_types trivial to add.

### When `final_text` is updated

When the clinician saves their (possibly edited) SOAP back to `recordings.soap_note`. Same DB transaction updates the most recent `generations` row for `(recording_id, output_type='soap')` where `final_text IS NULL OR regeneration_seq = max(regeneration_seq)`:

- If the most recent row has `final_text = NULL`, set it (first save of the current draft).
- If `final_text` already exists, replace it (clinician edited a previously-saved SOAP).

`finalized_at` is set/updated to `datetime('now')`.

### Regeneration

When the clinician clicks "Regenerate SOAP" without first saving the current draft:

- The previous row's `final_text` stays NULL forever.
- A new row is inserted with `regeneration_seq = previous + 1`.

If the clinician regenerates *after* saving (rare but real):

- The previous row's `final_text` is preserved (it represents what was saved).
- A new row inserts with `regeneration_seq = previous + 1`.

### Edit-distance computation

`edit_distance` and `edit_ratio` are computed async after `final_text` is set, via a small `tokio::spawn_blocking` task using a word-level Levenshtein on whitespace-split tokens. Word-level (not character-level) because the curate UI surfaces signal like "clinician changed ~20% of the words," which is more intuitive than character delta.

Failure to compute (panic, OOM) doesn't break the save — `edit_distance` simply stays NULL, and the curate UI shows it as "uncomputed."

### Failure modes

- **AI generation errors** → no row inserted. Standard error path.
- **Capture row insert fails after AI success** → `tracing::warn!` with `recording_id`, return draft to UI normally. The clinician sees the draft and can continue working; the data isn't captured, which is acceptable for a single-row miss.
- **Clinician closes app before saving** → row persists with `final_text = NULL`. Curate UI treats this as a rejected draft.

### Toggle

Single user-facing setting: **Settings → Training Corpus → "Capture generations for training corpus"**, default OFF.

- When OFF: no rows are inserted. Existing recordings work normally.
- When ON: every successful SOAP generation is captured.
- Toggling from ON to OFF does not delete previously captured rows; it just stops new captures.

## Phase 2 — Curate

### Surface

New tab in the existing Settings dialog: **"Training Corpus"**. Tab is visible only when capture has been enabled at least once (or always — UI decision deferred to design review).

### Three views (sub-tabs)

1. **Candidates** (default landing view)
2. **Promoted**
3. **Rejected** (collapsed by default; explicit access)

### Candidates view

- Paginated list of `corpus_status = 'candidate'`, ordered by `created_at DESC`.
- Per-row card:
  - Recording date + patient name (if set; else just date)
  - First ~150 chars of `draft_text`
  - First ~150 chars of `final_text` (or "(rejected — never saved)" if NULL)
  - Edit-ratio chip: green "light edit" (<15%), yellow "moderate" (15–40%), orange "heavy edit" (>40%), red "no save"
  - Three buttons: **Promote** / **Reject** / **Skip for now**
- Header strip: candidate count, total estimated tokens of currently-displayed candidates
- Keyboard shortcuts: `J`/`K` to navigate, `P`/`R`/`S` for promote/reject/skip, `Enter` to expand a row to full text

### Promoted view

- Paginated list of `corpus_status = 'promoted'`
- Read-only by default with an "Unpromote" button per row
- Header strip: promoted count, total estimated tokens (input + output)
- Filter: by `ai_model` (default: All)

### Rejected view

- Paginated list of `corpus_status = 'rejected'`
- "Restore to candidates" per row
- Lets the clinician un-do mistakes from batch curation

### Mutation semantics

Promoting / rejecting / unpromoting updates `corpus_status` and sets `corpus_curated_at = datetime('now')`. Single-row transactions; no batch API in v1 (a single click commits a single state change — simpler error surface).

## Phase 3 — Export

### Trigger

Button in the Promoted view: **"Export training corpus"**. Opens a confirmation dialog showing:

- Promoted-pair count
- Base-model filter (multi-select if corpus spans multiple `ai_model` values; default: most-recent model)
- Estimated token count for the filtered subset
- Redaction strictness (single choice: "standard" or "aggressive" — see Redaction section)
- Output directory chooser (defaults to `~/Documents/FerriScribe Training Corpus/`)

### Output structure

```
<output_dir>/training-corpus-YYYY-MM-DD-HHMMSS/
├── train.jsonl              # one JSON object per line
├── manifest.json            # counts, model filter, redaction settings, timestamp
└── README.md                # format docs, redaction caveats, suggested fine-tuning recipes
```

### JSONL format

Default: OpenAI chat-completion format — widest tool compatibility.

```json
{"messages":[
  {"role":"system","content":"<rendered prompt template>"},
  {"role":"user","content":"<input transcript + context, redacted>"},
  {"role":"assistant","content":"<final SOAP, redacted>"}
]}
```

Alternative format (configurable in the export dialog, deferred to design review): pure JSONL with named fields (`{"transcript":"...","soap":"..."}`) for tools that don't accept the chat-message shape.

### Redaction pipeline

For each promoted row:

1. Apply existing `PhiRedactor::redact` to `input_transcript`, `input_context_json` values, `draft_text` (if included), and `final_text`. Covers SSN, phone, email, DOB, MRN, addresses, ZIP.

2. Apply v1-extension redaction:
   - **Patient names** — build a regex from this recording's `patient_name` column (if set) and apply a literal+fuzzy match to all output fields. Patient name → `[PT_NAME]`.
   - **Recording-level identifiers** — `recording_id` UUID isn't included in output. The `output_type` is included. Date stamps in the format `YYYY-MM-DD HH:MM:SS` are scrubbed to `[DATETIME]`.

3. Apply v2-extension redaction (deferred unless requested at export time as "aggressive"):
   - **Provider names** — seeded from `saved_recipients` table (the clinician's referral list).
   - **Specific dates beyond DOB** — visit dates, "last Tuesday" temporal references.
   - **Locations / hospital names** — heuristic match against a project-shipped list of common Canadian hospitals + clinics.

4. If `PhiRedactor::contains_phi` still reports a match after redaction, flag the row in a `manifest.json.warnings` array. The export still succeeds, but the manifest documents which rows had residual signals.

### Manifest format

```json
{
  "schema_version": 1,
  "exported_at": "2026-05-11T22:30:00Z",
  "ferri_scribe_version": "0.10.55",
  "corpus_size": {"pairs": 1247, "input_tokens_est": 423000, "output_tokens_est": 187000},
  "base_model_filter": ["llama3:70b-instruct"],
  "prompt_template_filter": ["soap-default"],
  "redaction_strictness": "standard",
  "redaction_rules_applied": ["SSN","PHONE","EMAIL","DOB","MRN","ADDRESS","ZIP","PT_NAME","DATETIME"],
  "warnings": [
    {"row_index": 42, "reason": "residual phi detected after redaction"}
  ]
}
```

### Notes for the fine-tuner (in README.md)

The exported README explicitly documents:
- The chat-message format and how to feed it into common toolchains
- The fact that redaction has known false negatives (especially names not in `recordings.patient_name`)
- That the corpus is small-scale; LoRA/QLoRA preferred over full fine-tuning
- A pointer to typical hyperparameters for a personal-style fine-tune (LR ~2e-4, rank 16, 2-3 epochs)
- The base-model identifier the corpus was filtered to (so the clinician picks a compatible base)

## Edge cases

- **Recording deleted** → `ON DELETE CASCADE` removes all matching `generations` rows. Already-exported corpus files on disk are untouched.

- **Recording with no transcript** (STT failed) → no SOAP generation possible, no row inserted. Already handled by the existing pipeline.

- **Multiple SOAP regenerations against same transcript** → one row per generation, distinguished by `regeneration_seq`. Curate UI groups by recording_id with sub-rows.

- **Single recording with both SOAP and referral generated** → two rows with different `output_type`. v1 export only includes `output_type='soap'`. Future extension uses the same table.

- **Capture toggle turned OFF mid-session** → in-flight generations whose AI call already started complete normally and ARE captured if they started before the toggle changed. Newly-initiated generations after toggle-off are not captured. Simpler than mid-stream cancellation.

- **Toggle from OFF to ON** → only future generations are captured; existing recordings are not retroactively backfilled. Backfill is out of scope for v1.

- **App crash mid-generation** → AI call may or may not have completed. If it completed and the response was returned to the UI but the capture insert failed, that data is lost. Acceptable single-row loss.

- **Edit-distance computation panics** → row's `edit_distance` stays NULL. Curate UI shows "uncomputed" chip. Doesn't block anything.

- **Two clinicians on the same shared install (unlikely but possible)** → all corpus data belongs to whoever currently owns the install. Multi-user accounts are out of scope; if this becomes a real use case, it's a separate design.

- **Patient revokes consent for their data** → the clinician deletes the recording in the UI, which cascades. No special "revoke" flow needed in v1.

## Testing strategy

### Unit tests
- `generations` table CRUD: insert, update final_text, edit-distance computation, status transitions
- `PhiRedactor` extension: patient-name redaction with various capitalizations, partial matches, possessive forms ("Mrs. Johnson's")
- Edit-distance: word-level Levenshtein on representative SOAP-vs-edited pairs
- Cascade-delete: deleting a recording removes its generations rows

### Integration tests
- End-to-end capture: mock AI completion → row appears with correct fields
- Save flow: save SOAP → row's `final_text` populated, `recordings.soap_note` matches
- Regeneration: two AI calls → two rows, `regeneration_seq` incremented, first row's `final_text` stays NULL
- Capture toggle: OFF → no row; ON → row inserted
- Export: 3 promoted rows → JSONL with 3 entries, each redacted, manifest correct

### Manual / smoke tests
- Curate UI navigation with keyboard shortcuts
- Export dialog flow with multi-model corpus
- Real (or realistic-synthetic) SOAP with names, dates, addresses: confirm redaction works end-to-end
- Performance: capture overhead on a typical generation (target: <50 ms additional latency)

## Out-of-scope but worth flagging

- **Continuous evaluation** — once a clinician has a fine-tuned model, the app could automatically run their notes through both the base model and the fine-tuned model and report quality. Useful but separate feature.
- **Auto-detection of patient names without `recordings.patient_name`** — would need NER. Worth a v2 add if false-negative rate is bothersome.
- **Versioned templates** — if the SOAP prompt template changes between v0.10.x releases, mixing pre- and post-template data may confuse a fine-tune. Future work could version the template per-row.
- **Cross-clinician practice-level training** — explicitly deferred; would require consent infrastructure and aggregation server.
- **Patient-facing transparency** — eventually the app may want to surface "Dr. X is capturing your generated SOAP for AI training" to the patient. Not in v1 since data stays on the clinician's device.

## Open design questions for review

1. **Capture toggle default** — OFF (current spec) vs. prompt the clinician once at first launch ("Capture generations for training?"). Default OFF is the safe choice; ask if the user wants a one-time prompt.
2. **Export JSONL format** — default OpenAI chat-message vs. simple named-field. Currently chat-message; flag if you'd prefer the simpler format.
3. **Aggressive redaction in v1** — listed as v2-deferred; lift into v1 if you want it from day one.
4. **Settings tab visibility** — always visible vs. only after capture is enabled. Currently always visible.
