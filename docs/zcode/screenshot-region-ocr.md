# zcode prompt — Screenshot-Region → OCR → Clipboard

You are implementing a **screenshot-region → OCR → clipboard** feature in FerriScribe (Tauri 2 + Svelte 5 + Rust workspace, local-first AI medical scribe). Do not modify the OCR engine's logic or the privacy model. The feature mirrors Omarchy's `SUPER + CTRL + PRINT` binding: trigger → drag-select a screen region → the selected area is screenshotted, OCR'd, and the extracted text is written to the clipboard.

**Reference behavior (Omarchy's `omarchy-capture-text`):** `slurp` shows an interactive drag-select region and prints geometry; `grim -g "$GEOMETRY"` captures that region as a PNG; `tesseract stdin stdout --oem 1 --psm 6 -l eng --dpi 300 -c preserve_interword_spaces=1` extracts text; the text is written to the clipboard and a notification confirms it. FerriScribe's equivalent uses its own local vision model instead of tesseract.

**Hard facts about FerriScribe's existing infrastructure (reuse; do not reinvent or guess):**
- **OCR:** in `crates/processing/src/ocr/mod.rs`, `ocr_image_bytes(image_bytes, format, ocr_model, provider)` (line ~155) is a **private `async fn`** that base64-encodes an image and calls the configured **local** vision model — it is NOT re-exported (`crates/processing/src/lib.rs` exports only the `ocr` module; the public surface is `extract_text` (path-based), `OcrPageResult`, `OcrError`, and the pdfium helpers). Model name = `config.ocr_model` falling back to `config.ai_model` (see `crates/core/src/types/settings.rs`); provider resolved from `config.ai_provider` (pattern in `src-tauri/src/commands/ocr.rs` `ocr_documents`). Route the screenshot through `ocr_image_bytes` — do NOT introduce tesseract or any other OCR engine.
- **The ONE permitted OCR-crate change:** because `ocr_image_bytes` is private, making it callable is a required, explicit exception to "do not modify the OCR engine." Make `ocr_image_bytes` `pub` (or add a thin `pub` wrapper around it) and re-export it from the `ocr` module. **Zero changes** to its logic, prompt, timeouts, or tests — visibility only.
- **Clipboard:** `tauri-plugin-clipboard-manager` is already a dependency and `clipboard-manager:allow-write-text` is already granted in `src-tauri/capabilities/default.json`; frontend wrapper is `src/lib/utils/clipboard.ts` (`copyToClipboard`). Prefer writing from the Rust side so the flow completes even when the webview isn't focused.
- **Command pattern:** follow the existing `#[tauri::command]` + `State<'_, AppState>` pattern, register in `src-tauri/src/lib.rs` `generate_handler!`, add new permissions to `capabilities/default.json`.
- **Binary name:** the app binary is **`rust-medical-assistant`** (from `[package] name` in `src-tauri/Cargo.toml`), NOT "ferriscribe". All CLI/launcher references must use this name.
- **Confirmed net-new (zero matches in `src-tauri` today):** `tauri-plugin-global-shortcut`, `tauri-plugin-single-instance`, and any screenshot crate (`xcap`/`grim`/`slurp`/`screencapture`).

**What you must add:**
- **A headless trigger via single-instance + IPC delegation.** Add `tauri-plugin-single-instance`. A `--capture-ocr` CLI flag is parsed in `src-tauri/src/main.rs` **before** `rust_medical_assistant_lib::run()` (a thin wrapper there). When the flag is present: detect a running instance and delegate the capture to it via the single-instance `second-instance` callback (which triggers capture in the *already-running* app — do NOT boot a second full app shell, which would double-init keychain/SQLCipher/tray/webview). **Cold-start rule:** if no instance is running, do not start a full GUI to handle it — exit with a nonzero code and surface "start FerriScribe first" via desktop notification (NOT `println!` — the Windows release build sets `windows_subsystem = "windows"`, so there is no console and stdout is invisible).
- **Global shortcut.** Add `tauri-plugin-global-shortcut`. **Default binding: `CmdOrCtrl+Alt+O`** ("O for OCR") → `Cmd+Option+O` on macOS, `Ctrl+Alt+O` on Windows/Linux, configurable in Settings. **Pitfall:** the plugin only registers X11 global shortcuts on Linux — it will NOT fire under Wayland/Hyprland (compositor-owned hotkeys). On Wayland use the XDG portal GlobalShortcuts interface or rely on the compositor binding below. The feature must also be triggerable from inside the app (button + in-app shortcut) on every platform.
- **Omarchy compositor-binding leg.** On Linux/Wayland, the same `Ctrl+Alt+O` must be registered by the compositor, since the app cannot self-register there. **Omarchy is a Lua-configured Hyprland distribution** — emit the binding as an `o.bind(...)` line for the user's `~/.config/hypr/bindings.lua` (personal overrides):

  ```lua
  o.bind("CTRL + ALT + O", "FerriScribe OCR capture", "rust-medical-assistant --capture-ocr")
  ```

  For **vanilla (non-Omarchy) Hyprland** only, the equivalent is a `.conf` line: `bind = CTRL ALT, O, exec, rust-medical-assistant --capture-ocr`. Emit the Omarchy Lua form as primary and the `.conf` form as the generic Linux fallback. **INSTALL-time footgun:** pre-Quattro Omarchy (issue #6933) stored overrides in `~/.config/hypr/bindings.conf` and the upgrade silently stopped loading it — the installer instructions must tell users to **check which override file actually exists on their machine** (`bindings.lua` on current Omarchy vs. `bindings.conf` on pre-Quattro) and place the binding accordingly, never assume `bindings.lua`. Cross-reference with the install-asset PKGBUILD.
- **Screen-region capture** (drag-select + screenshot), priority order: macOS → `screencapture -i -x <tempfile>`; Linux Wayland → `slurp` + `grim` when available (matches Omarchy exactly), else XDG portal Screenshot; Linux X11 and Windows → a minimal transparent fullscreen overlay the user drags a rectangle on, then capture that rect via the platform screen API. Pass the PNG bytes to `ocr_image_bytes`.

**Privacy constraints (absolute — load-bearing, do not weaken):**
- OCR goes through the existing local vision-model path only. No cloud/hosted model, no telemetry, no new outbound network calls beyond the existing anonymous GitHub update check.
- **Captured screenshots are PHI.** Prefer holding the PNG bytes in memory. Where the platform capture tool can only write to disk — specifically macOS `screencapture`, which has no stdout mode — this is the one permitted exception: write to a **private, app-controlled temp directory** (app data dir, created `0700`, file opened `0600`), read the bytes immediately, then **shred and unlink the file before OCR completes**. On Linux (grim) and Windows (in-process capture), do not touch disk at all. Wherever bytes transit disk, the file lives in the private dir, is deleted in the same operation, and its name/path is never logged. Never write to a shared `/tmp`, and never persist the image after OCR.
- **Never** place screenshot *pixel data* on the OS clipboard — macOS/Windows sync clipboard history to the cloud by default. Only the final extracted *text* is ever written (that text is the intended persistent end state the user pastes from).
- **Never log** extracted text, screenshot bytes, or filenames that could carry content — log counts/lengths only (the existing OCR crate already does this; preserve it).
